# Auto-Harness 专家组决策与执行引擎

## 触发时机
当用户提出“需要规划下一个迭代”、“有多个技术方案需要决策”、“不知道该选哪个库”或触发了**方向性/架构性/成本分歧**时，Agent 应主动调用此 Skill 的逻辑。

## 协作原则：非技术 PM 模式
遵循全局《非技术产品经理协作模式》，Agent 在内部完成复杂的脑暴和技术推演，但**绝不擅自拍板核心方向**。推演完成后，必须把复杂的权衡浓缩为“1、2、3 单选题”交给用户做最终裁决。

## 输出展现规范 (Output Style Guidelines)

为了给用户提供最清晰、高级且极具专业感（WOW 效果）的交互体验，汇报时必须遵守以下格式规范：

1. **阶段化进度面板 (Progress Panel)**
   使用图标展示团队协作生命周期的当前阶段：
   - 🔍 `[阶段 1/3]` 需求分析与专家组建
   - 🤖 `[阶段 2/3]` 虚拟专家背靠背研讨与投票
   - 🗳️ `[阶段 3/3]` 方案提炼与高层请示（等待老板拍板）

2. **专家视角矩阵 (Expert Matrix)**
   展示专家研讨结果时，使用 Markdown 表格进行清晰对比：
   | 专家角色 | 核心立场 | 投票支持项 | 一句话裁决理由 |
   | :--- | :--- | :--- | :--- |
   | 👨‍💻 架构师 | 长期可维护性 | 方案 A | 解耦彻底，后期重构成本低 |
   | 👔 业务 PM | 快速试错交付 | 方案 B | 开发周期短，本周即可上线验证 |
   | 🛡️ 安全/运维 | 稳定与成本控制 | 方案 A | 方案 B 引入太多外部依赖，有漏水风险 |

3. **老板决策选项 (Executive Options)**
   在汇报的末尾，**必须**使用带明确序号的选项供用户直接选择（单选题）：
   > 🏆 **专家组建议推荐**：方案 A (得票 2/3)
   > 
   > **请老板（用户）定夺下一步方向：**
   > 1. **采用方案 A**（推荐，注重长期稳定，耗时约 2 天）
   > 2. **采用方案 B**（注重短期交付，耗时约半天）
   > 3. **都不选，我有其他想法**（请补充说明）

## 执行流程

1. **需求分析与选项提炼**
   主 Agent 提炼出 2-3 个核心的架构/技术路线候选项。
   定义 3 个不同的专家角色（如架构师、业务负责人、安全/测试工程师）。

2. **自动拉起讨论组 (Subagent Invocation)**
   后台通过 `invoke_subagent` 或在上下文中模拟专家思维逻辑。
   分析每个选项的优劣，并强制每个专家给出一个明确的**优先推荐项 (Vote)**。

3. **收敛与汇报 (Present to User)**
   主 Agent 汇总所有专家的结果，渲染《专家视角矩阵》，并严格按照《老板决策选项》格式输出 1、2、3 选项，停止生成，等待用户输入。

4. **自主推进与闭环 (Autonomous Execution)**
   用户输入数字（如 `1`）后，主 Agent 彻底接管执行。
   无需再向用户汇报中间的测试失败或编译报错，利用 S8 Quality Gate 在后台闭环重试，直到所有测试通过（跑通 `.harness/verify.sh` 或达成业务验收），最后向用户汇报最终效果。
